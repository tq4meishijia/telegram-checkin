## 4. 新发现问题

### N1 静态资源响应不带 CSP 头（dev 实测）— 严重度：低
- 位置：`wrangler.toml:15`（run_worker_first = ["/"]）与 `src/index.ts:70-75`（catch-all 附加 CSP）
- 描述：冒烟实测 `GET /` 返回 CSP 头，但 `GET /app.js`、`/style.css` 均不带 CSP 头（响应仅 Content-Type/Cache-Control/ETag/CF-Cache-Status）。wrangler.toml 注释声称「所有请求先打到 Worker……静态响应才能统一附加 CSP」，与 wrangler 4.141.0 dev 模式实测不符——dev 下 assets 层直接服务了 JS/CSS，未经过 worker catch-all。单测环境（直接 app.fetch）所有路径都经 catch-all，故 api.test.ts:278 的 CSP 用例无法暴露此差异。
- 影响：安全影响有限——CSP 是文档级策略，真正起作用的 HTML（/）已带头且 script-src 已收紧至 'self'；JS 文件自身响应头带不带 CSP 无实际防护意义。属于「注释/预期描述与 dev 实测行为」的偏差。线上（真实 Cloudflare）run_worker_first 为前缀匹配，"/" 理论上匹配全部路径，线上行为可能与 dev 不同，未在本次验证范围。
- 修复建议：二选一——(a) 若意图就是仅 HTML 带头：修正 wrangler.toml 注释，避免误导；(b) 若要求静态资源也带头：将 run_worker_first 调整为 ["/", "/app.js", "/style.css"] 并回归验证。

### N2 单套件偶发 flaky — 严重度：低
- 位置：疑似 `tests/runner.test.ts` capture_reply 用例或 `tests/api.test.ts`（未捕获到确证）
- 描述：8 次完整运行中 1 次出现 1/72 失败，4 次连续重跑均全绿。
- 影响：CI 可能偶发失败，损害交付信号可信度。
- 修复建议：CI workflow 加 `vitest run --retry 1`；或定位时序敏感用例改用 fake timers。
